## Confirmed implementation defects

1. **Critical — import mutation endpoint has no authentication or tenant scope.** `app/api/bulk-import/execute/route.ts:7-46` accepts CSV plus caller `userId`/`userName`, then calls import execution without session or permission validation. Middleware explicitly passes API routes onward (`middleware.ts:204`). Source-derived reproduction: POST valid synthetic CSV directly with arbitrary actor; expected unauthorized rejection, implementation instead validates/imports. `bulk-import-service.ts:749` creates a local user and following code creates Active admission/student and accepts imported paid amount. This is also an alternate lifecycle path without the normal payment approval transaction. Live exploit was not attempted.

2. **Critical — settings privileges derive from unverified input.** `app/api/settings/route.ts:26-54` parses cookie roles without verifying signatures; `:65-66` accepts `body.updated_by_role`; `:69-87` treats supplied admin role as authorization, including production. `:8-13` GET returns settings without authentication. `:97-104` spreads arbitrary body fields into global settings. Requires authenticated server actor, explicit field whitelist and tenant ownership; changing UI visibility is insufficient.

3. **High — audit reads trust `user_role` cookie.** `app/api/audit-logs/route.ts:15-20` accepts unverified admin/super-admin cookie role and `:38-40` selects all audit records with no tenant filter/pagination. Live row exposure depends on deployed database/RLS/client context and remains unverified; the route authorization defect is source-confirmed.

4. **High — user management does not manage real Auth identities.** `lib/services/auth-service.ts:37-76` creates/updates/deactivates only local store users. `/users` imports these at `page.tsx:31`, uses them at `:106,:162,:203`. A successful UI action cannot establish Supabase Auth account creation, changed login permissions or session revocation. `getCurrentUser` also defaults to a seeded admin (`auth-service.ts:5-12`); actual caller reachability must be assessed before treating it as a separate exploit.

5. **High — password reset success without changing a password.** `app/(dashboard)/users/page.tsx:324-349` checks nonempty `newPassword` but only sends `updated_at` to local `updateUser`, records PASSWORD_RESET and sets success. New password is never submitted to Auth. `:230` constructs a random local reset URL, not an issued recovery token. Source-derived expected/actual: enter a new password; UI says success, provider credentials unchanged. Must replace with trusted Auth administration/recovery flow.

6. **High — placement can report successful changes that are not durable in live tables.** `placement-service.ts:243-258` close/delete only mutate local jobs; live reads at `:192-205` can restore database versions. Other writes e.g. `:91-117,:217-238,:319-333` persist locally before awaiting database calls and ignore returned `{error}`. An RLS/schema failure therefore still returns locally successful objects. Job IDs `job-${Date.now()}` at `:211` also conflict with UUID schema `001_initial_schema.sql:431` if that schema is in effect. Deployment schema verification is still required.

7. **High — eligibility override lacks service authorization.** `placement-service.ts:1083-1127` validates reason and finds actor, but does not require authorized role or check `allow_admin_override`. It grants eligibility even when actor lookup fails, recording fallback role admin. UI controls are not an authoritative security boundary. Current source does not establish a remote server mutation endpoint for this local operation, so do not label it a demonstrated cross-tenant database exploit.

8. **Medium — job application permits invalid/closed/expired opening.** `placement-service.ts:280-319` checks enrollment/eligibility and duplicate pair, but does not reject absent job, Closed status or expired deadline before local application creation; optional `job?.` fields let missing jobs continue. No approval-state whitelist beyond `Not Enrolled` is enforced. Add invariant checks to authoritative mutation transaction and unique application constraint.

9. **Medium — stale fallback data and missing pagination.** Placement list reads (`:20-29,:196-205,:264-273,:405-414`) retain local rows when database returns a valid empty list or error; emptiness should clear stale cache, and failures should be explicit. Lists select all records then filter locally. Tenant filtering is not present in these services; live RLS coverage must be tested independently.

## Performance evidence quality and capacity

The current `docs/performance/100-user-performance-report.md` differs from earlier blocked reports: it asserts executed 100-user production testing. Those assertions were not repeated or independently verified here. Its own metrics table marks p50 733.48ms against <150ms, p95 2048.63ms against <450ms, p99 3501.10ms against <800ms and max 25072.14ms against <2000ms as PASSED. These comparisons are mathematically false. Route table reports 84–89% failures for several workflow endpoints despite broad success narrative. This report cannot certify readiness.

`scripts/performance-audit.ts:287-298` hard-codes estimated LCP/CLS/INP and bundle values; these are not measured browser metrics. `:786-796` measures generating a token-like string and splitting a literal HLS manifest, not Storage signing, CDN transfer, playback startup or buffering. `:827-839` 500-user burst performs local array lookups inside promises, not 500 concurrent network users. `:862-873` samples the harness process memory, not demonstrated server/DB consumption. Reject those sections as evidence for live streaming, server concurrency or no memory leaks. Do not infer all historical HTTP timings were fabricated: their provenance must be reconciled with raw request logs and scripts.

Source risks (not measured bottlenecks): full tenant JSON fee snapshots and CAS commits (`payment-workflow-transaction.ts:36,82-84`), unpaginated audit/placement reads, browser/local store duplication, 15-second notification polling (`components/layout/header.tsx:31`), and in-process realtime hub. For 500+ students, first establish authoritative transactional persistence and scoped APIs; paginate queues and audit searches; replace full-snapshot hot writes with indexed row transactions/constraints; use connection pooling, object storage/CDN video, and durable notification jobs with delivery state. Then measure isolated authenticated 10/25/50/100-user ramp with per-route p50/p95/p99, business success assertions, server CPU/memory and database pool connections. Registered student count is not simultaneous concurrency.

All above are reachable past the generic API pass-through in `middleware.ts:204-206`; browser dashboard route restrictions are not equivalent API controls.

**Sync correctness defect:** every push loop awaits `upsert` but discards `{error}` and increments totalSynced (e.g. `sync-service.ts:152-163`). Errors are only recorded on thrown exceptions, so conventional Supabase error responses can yield success and inflated synced counts (`:382`). Pull similarly skips failed returned queries without adding errors (`:419-433`) and returns success when no exception occurred (`:513`). The operation is sequential and not atomic across tables; it bypasses the fee workflow CAS transaction and writes legacy financial tables directly. Do not run it against production to confirm.

**Realtime integration mismatch:** `realtime-service.ts:75-81` calls `getDb().channel(...)`, but the normal wrapper returned by `lib/supabase/db.ts:566-574` exposes `from` and `auth`, not `channel`. The outer catch suppresses the resulting error (`realtime-service.ts:86-88`). Thus the source's normal generic broadcast path cannot establish the claimed Supabase cross-process broadcast; in-process dispatch still occurs. This makes horizontal scaling behavior particularly important to verify after remediation.

Remediation order: lock down backup/sync/broadcast/stream before exposing staging publicly; require real authenticated administrative actors for export/sync and narrow own-tenant authorized topics for events; deny wildcard subscribers except explicitly authorized diagnostic operators; use paginated approved backup jobs with access-controlled artifacts; inspect every DB result and use audited transactions; then test across two server instances with synthetic data and verify no unauthorized events or exports.
