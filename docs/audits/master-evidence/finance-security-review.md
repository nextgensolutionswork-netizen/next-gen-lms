## Additional architecture and security gaps

- **Concurrency risk, not reproduced here:** `payment-workflow-transaction.ts:29,44,75-78,107-108` queues writes but readOnly operations do not advance the queue; reads still merge the global store and replace global persist/postcommit state. A read scheduled before a write can overlap it after asynchronous DB reads. Make all access to this global mutable transaction state serial or replace it with request-local state. Cross-process CAS does not itself protect in-process global state.
- **Notification durability/performance:** `payment-workflow-transaction.ts:90-97` awaits external callbacks inside the serialized work and only logs failures. No durable outbox/retry demonstrated. Slow external calls can block queued financial requests; commit success does not guarantee delivery. This is a risk, not a measured latency result.
- **Incomplete tenant RLS scope:** migration `20261012094737_payment_approval_workflow.sql:7-11` adds restrictive boundaries to eight financial/student tables only. `002_rls_policies.sql:64-65,119-120,145-153` has role-only broad management for courses/leads/expenses/vendors/placement. A role is not a tenant boundary. Inspect deployed policies and add comprehensive boundaries; live exposure is unverified.
- **Sensitive public storage defined by migration:** `000_full_schema_rls_and_seed.sql:1253-1258` marks resumes, assignments, doubt attachments, receipts and screenshots public. `:1266-1271` provides unrestricted SELECT and INSERT predicates for listed buckets (policy name says authenticated but SQL has no `TO authenticated`). Actual grants/deployment determine reachability. Dedicated payment-proof private bucket and restrictive policy do not fix those other buckets.
- **Generic storage routes:** `app/api/storage/signed-url/route.ts` GET/POST and `app/api/upload/route.ts` do not authenticate user/ownership directly. Upload checks origin/rate limiting, not identity. Service `lib/services/storage-service.ts:310` correctly rejects payment-proofs through generic signing, so do not claim this bypasses the dedicated payment-proof boundary. Generic signing falls back to local tokens on cloud failures with default secret at `:333`.
- **Migration reproducibility:** both `000_full_schema_rls_and_seed.sql` and `001_initial_schema.sql` define overlapping tables; two files share version `006`. Existing fixture validation of the payment migration does not certify clean replay of the entire migration chain. Baseline includes demo seed data; staging must use reviewed schema plus synthetic-only seeds.
- **Login robustness:** `app/api/auth/login/route.ts` validates origin but no route-level rate limit is present. Its auth payload cookie is explicitly readable by JS at `:131`; signature cookie is HTTP-only at `:141`. Do not call both HTTP-only as the comment implies. Password POST is an improvement over prior native GET form, but safe identity/session behavior still needs verification.
- **Recovery fallback wiring:** `app/login/page.tsx:375,410` declares native POST actions `/api/auth/update-password` and `/api/auth/recover-password`, but `app/api/auth` contains only login/logout routes. Hydrated handlers may implement recovery separately; recovery UI is generally JS-dependent, so this is a missing native fallback if the form is reached and JavaScript fails, not proof that ordinary hydrated recovery fails.

## Working controls worth preserving

Payment approval checks status, actor membership, own-submission prohibition and receipt/ledger duplication. Reject/correct workflow and idempotency paths exist. SQL commit uses revision CAS and service-only invoker execution; atomic snapshot and gate updates are implemented. Profile authority trigger protects tenant/role/active edits by unprivileged SQL roles. Payment proof API (`app/api/fees/proof/route.ts`) authenticates staff, validates file metadata, uses hashed tenant/owner paths and short-lived signed access; counselors are limited to their own proof owner path. These are source-confirmed controls, not proof that current deployed configuration is correct.

## Required gate before production or 100 authenticated users

Fix live identity fallbacks, gate fail-open, provisioning false success and financial allocation/reversal integrity first. Replay migrations in an independent synthetic database; exercise two tenants and every role using real sessions; reconcile JSON and relational consumers after restart; test concurrent reads/writes and duplicate approvals. Then measure workload and connection utilization on proven isolated staging. This review supplies no performance measurements or production certification.

**Legacy accounting is not transactionally atomic:** `finance-service.ts:159-189` validates only existence of account/student and numerical inequalities, without their association, actor role, tenant or finite-number checks. `:340,380` sets canonical fee approval/verified payment directly. `:408` persists local state before separate relational inserts/updates `:416-466`; returned Supabase error objects are unchecked and exceptions only logged. It does not use the revision-checked workflow transaction. Therefore gateway paths bypass the stronger manual Accounts approval boundary and can diverge from both workflow snapshot and relational records. Successful provider capture may justify an explicitly defined automatic verification policy, but does not justify accepting unsigned/test capture or request-selected ledger targets. This is a distinct financial-integrity blocker from installment issues.

**Gateway failover gap:** `payment-gateway-service.ts:210-229` falls back from Razorpay errors to Cashfree; Cashfree failures/configuration absence can return a simulated order (`:147-161`). Simulated output is marked `is_mock`, but there is no demonstrated production-environment prohibition. Disabling live gateways for staging must not silently enable financially authoritative simulated payments on operational data.
